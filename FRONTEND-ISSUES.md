# Frontend Issues Handoff

## 1. Task assignment is not working

### Backend contract

The task API accepts an assignee's MongoDB user ID:

```text
POST /api/v1/tasks/:projectId
PUT /api/v1/tasks/:projectId/t/:taskId
```

Example JSON:

```json
{
  "title": "Task title",
  "description": "Task description",
  "status": "todo",
  "assignedTo": "USER_OBJECT_ID"
}
```

The `assignedTo` value must be `member.user._id` from:

```text
GET /api/v1/projects/:projectId/members
```

Do not send the username, email, display name, member document ID, or the
entire user object.

The backend now verifies that the assignee is a member of the selected
project. A user from another project cannot be assigned to this task.

### Frontend checklist

- Load project members before rendering the assignee selector.
- Use `member.user._id` as the option value.
- Use `member.user.fullName` or `member.user.username` only as the label.
- Include `assignedTo` in the final create/update request.
- When using `FormData`, append it as a string:

  ```ts
  formData.append("assignedTo", selectedMemberUserId);
  ```

- Do not manually set `Content-Type` for `FormData`.
- After creation/update, use `payload.data.assignedTo` to display the saved
  assignee.

Expected errors:

- `400 Assigned user is not a member of this project`: wrong ID or stale
  member/project state.
- `404 Assigned user not found`: the user was deleted.
- `401 Invalid access token`: the local session is expired or missing.
- `403`: the authenticated user cannot manage tasks in this project.

## 2. Task detail does not show which project it belongs to

The task detail response now includes:

```json
{
  "project": {
    "_id": "PROJECT_OBJECT_ID",
    "name": "Project name",
    "description": "Project description",
    "status": "Planning",
    "startDate": "2026-10-07",
    "endDate": "2026-10-10"
  }
}
```

Render the task detail heading using the task title and show the project name
as context:

```tsx
<h1>{task.title}</h1>
<p>{task.project?.name ?? "Project unavailable"}</p>
```

The text `create new task` in the screenshot is frontend heading content; it
is not generated by the backend. The frontend should use the actual task title
after loading the task, and use a larger heading style for the title.

## 3. Status shown in the task detail does not match the selected status

Task status values are lowercase API values:

```text
todo
in_progress
done
```

The frontend may display labels such as `To Do`, `In Progress`, or `Done`, but
must send the lowercase API value. Do not send project statuses such as
`Completed` to the task endpoint.

After a successful update:

```ts
const payload = await response.json();
setTask(payload.data);
```

Do not keep displaying the previous task object after a successful update.

## 5. Task list crashes with `projectId is not defined`

### Observed error

```text
task-list.tsx:78 Uncaught ReferenceError: projectId is not defined
```

### Cause

The `TaskList` component references `projectId` inside the `tasks.map(...)`
callback, but `projectId` is not declared in that component's scope or passed
as a prop.

This crashes the whole task list during render. The backend cannot fix this
error because it occurs before any API request is made.

### Immediate fix

Change the component signature from something like:

```tsx
function TaskList({ tasks }: { tasks: Task[] }) {
```

to:

```tsx
type TaskListProps = {
  tasks: Task[];
  projectId: string;
};

function TaskList({ tasks, projectId }: TaskListProps) {
```

Then pass the selected project ID from the parent:

```tsx
<TaskList
  tasks={tasks}
  projectId={selectedProjectId}
/>
```

If the parent uses a project object, pass:

```tsx
projectId={selectedProject?._id ?? ""}
```

Do not use an undeclared variable such as `projectId` inside the `map`
callback, and do not use the project name or array index as the ID.

### Fix option A: pass the project ID as a prop

```tsx
type TaskListProps = {
  tasks: Task[];
  projectId: string;
};

function TaskList({ tasks, projectId }: TaskListProps) {
  return tasks.map((task) => (
    <TaskRow
      key={task._id}
      task={task}
      projectId={projectId}
    />
  ));
}
```

The parent should render it with the selected project's backend ID:

```tsx
<TaskList tasks={tasks} projectId={selectedProjectId} />
```

### Fix option B: derive it from each task

Use this only when the task list response includes a populated project:

```tsx
const taskProjectId =
  typeof task.project === "string" ? task.project : task.project?._id;
```

The backend task-detail response includes the populated project. If the list
endpoint is used for task rows that need a project ID, either pass the current
project ID from the page or update the list API/query to include it.

Do not reference a bare `projectId` variable unless it is declared in the
component or received through props. This error occurs during rendering,
before any task action can run.

## 6. Subtask update controls are missing

The backend already supports updating a subtask. The task-detail UI should
provide:

- An editable title field or edit action.
- A completion checkbox/switch.
- Save and cancel controls while editing.
- A delete action if the current user can manage tasks.

### Update endpoint

```text
PUT /api/v1/tasks/:projectId/st/:subTaskId
```

Request body:

```json
{
  "title": "Updated subtask title",
  "isCompleted": true
}
```

Only include fields that changed. After a successful response, replace the
subtask in local state with `payload.data`, or reload the task detail:

```ts
const payload = await response.json();
setSubtasks((items) =>
  items.map((item) => (item._id === payload.data._id ? payload.data : item)),
);
```

The delete endpoint is:

```text
DELETE /api/v1/tasks/:projectId/st/:subTaskId
```

The frontend must pass the selected project's backend `_id` in the URL. The
backend now also verifies that the subtask belongs to that project before
updating or deleting it.
